dPLaaX DID OAuth Grant Type

This page is the namespace document for the OAuth 2.0 extension grant type (RFC 6749 §4.5) identified by:

https://dplaax.dev/oauth/grant-type/did

The identifier is compared byte-for-byte by the token endpoint and is never dereferenced at runtime. Its meaning is frozen: semantic changes to the grant will be published under a new URI.

What it does

Exchanges a DID-signed assertion for an access token. The client proves control of a did:dplaax DID by signing a short-lived message with the DID's key; the authorization server resolves the DID document from the dPLaaX registry named in the DID, verifies the signature against the published key, and issues a token whose subject is the DID.

Token request

POST /oauth/token with Content-Type: application/x-www-form-urlencoded:

FieldValue
grant_typehttps://dplaax.dev/oauth/grant-type/did (exact string)
client_ida registered OAuth client (public clients use tokenEndpointAuthMethod: none)
didthe authenticating did:dplaax DID
messageJSON: {"did": <same DID>, "timestamp": <RFC 3339>, "nonce": <random>}
signaturesignature over the exact message bytes, base64

The default signature algorithm is ed25519_raw (a raw Ed25519 signature over the UTF-8 message bytes); deployments configure the accepted set. Messages are single-use (nonce replay is rejected) and expire after a configured maximum age.

Response

On success: a standard OAuth token response (access_token, token_type: Bearer). On failure: standard OAuth error responses (invalid_request, invalid_client, invalid_grant, unsupported_grant_type).

Reference implementation

The grant is implemented by the @provin-line/auth-provider-did package of the dPLaaX auth stack, which also documents the full wire contract and the configurable algorithm set.

Extending

Deployments that extend the wire protocol (for example, to embed a Verifiable Presentation) should define a new grant type under a domain they control (e.g. https://example.com/oauth/grant-type/did-vp) rather than reusing this identifier.
